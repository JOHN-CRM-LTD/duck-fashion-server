# Points to coupons in Internal Chat

Duck owns the rewards, member ledger and issued coupon records in its existing SQLite database. John CRM uses the configured Coupon endpoint and its existing hosted coupon page, including the workspace's saved design.

## Showcase
- A verified WhatsApp member with 720 points can ask "What can I do with these points?"
- The fresh rewards read lists item vouchers with their point costs, plus a HK$5 coupon for 500 points and a HK$12 coupon for 1,000 points. Affordability comes from the current source balance.
- "I'd like the HK$5 coupon" produces a summary: 500 points, 720 → 220, and a confirmation reference.
- Reply `CONFIRM L-...` to the delivered summary. Duck debits the points and issues a `DF-...` coupon. The reply contains that exact code and the existing `/api/public/coupons/<opaque-token>` link.
- The page uses Duck's exact `br_no`, `statement_desc`, `coupon_amt` and `expiry_date`. Coupons expire 30 days after issue. Item vouchers do not reserve inventory.

A plain "yes" can confirm only the latest proposal. A proposal lasts 15 minutes; a confirmed attempt with an uncertain result can still be retried afterwards with the same reference. Duck persists the request key and coupon in the same transaction as the debit. Retries, including after a server restart, return the original coupon.

## Activate after deployment
1. Deploy the Duck server code without replacing its database, existing customer records or connection keys. Startup adds the coupon tables and missing demo offers idempotently.
2. Ensure the HTTPS reverse proxy forwards these POST paths to the existing stock service (removing the `/stock-api` prefix just as for its GET routes):
   - `/stock-api/bonus/redeem` → `/bonus/redeem`
   - `/stock-api/coupons/login`, `/stock-api/coupons/OpenAPI`, `/stock-api/coupons/Logout` → their `/coupons/...` paths
   Keep the paths authenticated by the service; do not expose other staff routes.
3. Deploy CRM, including migration `0258_loyalty_coupon_proposals`. Its `APP_URL` must be the public CRM origin.
4. In Duck's existing Coupon endpoint, save the configuration generated by `scripts/duck-fashion/coupon-setup.ts`. Set `DUCK_DEMO_MEMBER_PHONE` to a full registered demo phone and run `node --import tsx scripts/duck-fashion/coupon-setup.ts`. The result is a configuration template, with no credentials.
5. Enter encrypted credentials in the endpoint's existing credential fields: login username and user ID are `duck`; both passwords are the existing Duck staff write key. The read and staff-read keys cannot redeem points or access the coupon feed. Keep the write key out of knowledge documents and ordinary read connectors.
6. Test the saved connection, then activate it. This is a read of the coupon feed, with no AI call or points deduction. An empty coupon feed is valid before the first redemption. Preserve any existing campaign configuration; this chat workflow does not need an outbound campaign.
7. Select this endpoint under Automations → Loyalty → Points coupon endpoint and save. Keep the balance, rewards and cash-scheme connectors bound to Duck as before.

The previously diagnosed reward-code dependency bug is fixed in CRM main `48cd21be`. This feature also forces a fresh rewards read for explicit points-use questions and accepts the balance included in a verified personalised rewards response. Real source failures remain guarded; the AI cannot fabricate balances or successful redemptions.

Website chat can read the public reward catalogue. Personal balances and spending require the actual registered WhatsApp sender; typing another phone/member ID in chat never grants access.

## HTTP contract
`POST /bonus/redeem`, Bearer staff write key, JSON:
```json
{"member":"<verified source member>","phone":"<full verified phone>","rewardId":"CASH-500","expectedPoints":500,"expectedAmount":5,"expectedName":"Duck Fashion HK$5 cash coupon","requestId":"<stable proposal request key>"}
```

The source independently verifies the member/phone pair and exact current quote. Insufficient/expired points, a changed offer or reused key with different data fail without a debit. It consumes the earliest-expiring valid points first. The authenticated BOSS-compatible coupon feed returns the same issued coupon data.

## Verification
Tests use isolated PostgreSQL, local SQLite and mocked network/model calls. They cover the native chat tools, explicit confirmation, identity/workspace checks, source replay, coupon-page rendering, duplicate requests, partial failure rollback and SQLite restart durability. No paid AI evaluation or customer message is required for these checks.

A deployed showcase additionally requires the source POST paths, tested active endpoint and loyalty binding above. Local passing tests are not proof that those production settings have been activated.
